# 社内アプリ

GitHub Pages で配信している社内向けのアプリ置き場です。

| アプリ | 場所 | 誰が使うか |
|---|---|---|
| お客様連絡（管理） | `renraku/` | 事務所。要ログイン |
| 工事予定の入力（業者） | `gyousha/` | 施工業者。URLのトークンで入る |
| 業務チェックリスト | `index (2).html` | 総務 |

---

## お客様連絡アプリ

週の工事予定をまとめて、プランナーへ渡す文面を作ります。

```
業者さんがスマホで ○×と作業内容を入れる
        ↓
事務所が整えて、文面を作る
        ↓
プランナーの共有トークへ貼る
```

以前は共有ドライブの単一HTMLファイルでしたが、それだと
**携帯から開けない**、**業者が入れたものを事務所が見られない**、の2つが原理的に解けません。
どちらも「データの置き場所が各自のブラウザの中にしかない」ことが原因なので、
Firestore（クラウドの保管場所）へ移しました。

### 守りの考え方

このアプリはサーバーを持たない静的なページです。画面の JavaScript は誰でも読めるし、
書き換えることもできます。**つまり守りは `firestore.rules` にしかありません。**
画面側のチェックは使い勝手のためのもので、守りとして数えないでください。

線は2本だけです。

| 誰 | どうやって入るか | できること |
|---|---|---|
| 事務所 | 会社の Google アカウント（`@archigarden.net`） | 全部 |
| 施工業者 | 事務所から渡したURLのトークン | 自分の担当現場の、○×・作業内容・注意事項だけ |

業者のデータを `renrakuGyousha/{トークン}/weeks/...` という形で置いているのには理由があります。
Firestore のルールは**リクエストのパスしか見られない**ため、トークンをパスに含めないと
「トークンを知っている人だけ」を表現できません。別の場所に移すと鍵が鍵として働かなくなります。

### このリポジトリは公開です

そのため、次を必ず守ってください。

- **お客様名・プランナー名・業者用URL・LINE WORKS のキーをコードに書かない。** すべて Firestore に入れます
- `assets/js/firebase-config.js` に入る値は秘密ではありません（ブラウザに配る前提のもの）。守りはルール側です

`npm test` に、トークンらしき文字列がコードに混ざっていないかを見るテストを入れてあります。

## はじめる前の用意（1回だけ）

Firebase コンソールでの操作が要ります。順番どおりにお願いします。

### 1. Firebase プロジェクトを作る

1. https://console.firebase.google.com/ を開く
2. 「プロジェクトを追加」→ 名前は分かるもの（例：`archigarden-renraku`）
3. Google アナリティクスは**要りません**（オフでよい）

### 2. Firestore を作る

1. 左の「構築」→「Firestore Database」→「データベースの作成」
2. ロケーションは **`asia-northeast1`（東京）** を選ぶ
   ※ **あとから変えられません。** 迷ったらここで止めて相談してください
3. モードは「**本番環境モード**」を選ぶ（テストモードは30日で誰でも読み書きになります）

### 3. ルールを入れる

1. Firestore の「ルール」タブを開く
2. このリポジトリの [`firestore.rules`](firestore.rules) の中身を**全部**貼り付ける
3. 「公開」を押す

**ここを飛ばすと、誰も何もできない（本番環境モードの既定は全部拒否）か、
逆に全部筒抜けになります。** 必ず入れてください。

### 4. ログインを使えるようにする

1. 左の「構築」→「Authentication」→「始める」
2. 「Sign-in method」→ **Google** を選んで有効にする
3. 同じ画面の「設定」→「承認済みドメイン」に次を足す

```
shingonishimura0729.github.io
```

**これを足さないと、ログインのポップアップが開いた瞬間に閉じます。**

### 5. 接続先をこのリポジトリに書く

1. Firebase の「プロジェクトの設定」（歯車）→ 下の「マイアプリ」
2. ウェブアプリ（`</>` のアイコン）を追加。名前は何でもよい。Hosting は**使いません**
3. 表示される `firebaseConfig` の中身を、
   [`assets/js/firebase-config.js`](assets/js/firebase-config.js) の同じ名前の場所に貼り替える
4. 保存して、GitHub に push する

### 6. GitHub Pages を確かめる

リポジトリの「Settings」→「Pages」で、Source が `main` ブランチのルートになっていること。

公開先： https://shingonishimura0729.github.io/soumugyoumukannri/

## 使いはじめの順番

用意ができたら、管理画面で**この順**に登録してください。順番が違うと選べません。

1. **業者・URL** で施工業者を足す → その業者の「URLを発行する」を押す
2. **プランナー** で送付先を足す
3. **現場** で現場を足す（業者とプランナーを選ぶ）
4. 業者さんに、発行したURLをトークで送る

以降は毎週、**今週の予定** を開けば業者の入力が入っています。
整えて「文面をコピー」で、プランナーの共有トークへ貼ってください。

### 渡すURLについて

業者用URLは**それ自体が鍵**です。知っている人は入力画面を開けます。

- 相手のトークにだけ送ってください
- 渡し間違えたら「止める」を押すと、その場で使えなくなります
- 止めたあとは「URLを発行する」で新しいものを出し、改めて送ってください

## まだできていないこと

- **プランナーのトークルームへの自動送信。** いまは「文面をコピー」して手で貼る運用です。
  自動で送るには LINE WORKS のキーを隠す場所（サーバー）が要るため、
  静的ページだけでは完結しません。別途、既存の Bot サーバーに送信口を足す形になります
- **写真の受け取り。** 今回は入れていません（2026-09-25 決定）

## 開発するとき

```bash
npm test          # テストを流す。npm install は要りません
```

Node の標準機能だけで動くようにしてあります。テストは3種類です。

- `tests/domain.test.js` … 日付の計算と文面の組み立て。**文面の形を固定する**ためのもの。
  ここが赤くなったら、受け取る側が気づく変化が起きています
- `tests/pages.test.js` … 画面が開いた瞬間に壊れないか（構文・id・import）
- 同じく `tests/pages.test.js` … 公開リポジトリに秘密が紛れていないか

ブラウザで動かして確かめるときは、`file://` ではなく簡易サーバー越しに開いてください。
ES モジュールは `file://` では読み込めません。

```bash
npx serve .       # あるいは python -m http.server
```

## ファイルの並び

```
index.html              入口
renraku/index.html      管理画面（要ログイン）
gyousha/index.html      業者の入力画面（トークンで入る）
assets/js/domain.js     日付の計算と文面の組み立て。画面もFirestoreも持ち込まない
assets/js/firebase.js   Firebase への入口。読み込み先のバージョンをここに集約
assets/js/firebase-config.js  接続先。ここだけを書き替える
assets/css/app.css      共通のスタイル。スマホ前提
firestore.rules         守り。**ここが本体**
tests/                  テスト
```
